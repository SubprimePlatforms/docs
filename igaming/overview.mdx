> Purpose-built checks for online gaming and betting operators — detect VPNs, block ineligible jurisdictions, catch spoofed liveness capture, stop multi-accounting, and enforce self-exclusion.

deepidv's iGaming module adds four fraud and compliance checks on top of your existing verification flow, plus a self-exclusion registry your operator can manage per organization. It's designed for the risk signals that matter most in regulated online gaming: is this applicant using a VPN to mask their location, are they physically located somewhere you're licensed to serve, is their liveness capture being faked with a virtual camera or emulator, and have they — or their device's face — already excluded themselves from play.

## Two ways to run a check

<CardGroup cols={2}>
  <Card title="Workflow steps" icon="diagram-project">
    Add `IP_JURISDICTION`, `VPN_DETECTION`, `INJECTION_DETECTION`, or `ANTI_CHEAT` to a [workflow](/api-reference/workflows/create-workflow) with its config. The check runs automatically inside the hosted verification flow alongside your other services.
  </Card>

  <Card title="Standalone calls" icon="plug">
    Call `POST /v1/igaming/{injection,vpn-detection,ip-jurisdiction,anti-cheat}` directly with a `session_id`, supplying each check's inputs in the request body. You still configure the check's thresholds and actions on the session's workflow step.
  </Card>
</CardGroup>

Both paths write to the same session and produce the same verdict and action model. Either way, a check's **thresholds and enforcement actions come from its workflow step config** — the standalone request body carries only the check's inputs. Configure the step first ([Create workflow → Step configuration](/api-reference/workflows/create-workflow#step-configuration)). VPN detection, IP jurisdiction, and anti-cheat skip evaluation when their step is absent from the session's workflow (`UNAVAILABLE`/`allow`). Injection detection is the exception: with no step it still scores the supplied signals using the default config, which blocks on detection — so don't call it on sessions whose workflow lacks the step.

<Note>
  The iGaming checks are **not available in sandbox mode**. Sandbox keys can't create sessions (writes are rejected) and the `/v1/igaming/*` routes have no sandbox fixtures. Test with a live API key against a dedicated test workflow, and use [Purge enrollment](/api-reference/igaming/purge-enrollment) to reset enrolled test faces between runs.
</Note>

## The check catalog

| Check | What it catches |
| --- | --- |
| **Injection detection** (`injection-detection`) | Virtual cameras, emulators, and injected media during liveness capture |
| **VPN detection** (`vpn-detection`) | Applicants masking their real location behind a VPN, proxy, or relay |
| **IP jurisdiction** (`ip-jurisdiction`) | Applicants connecting from a jurisdiction you're not licensed to serve |
| **Anti-cheat** (`anti-cheat`) | Duplicate accounts (same face, new identity) and self-excluded applicants |

See [iGaming checks](/igaming/checks) for the inputs, verdicts, and session data each one persists.

## Verdict, action, and session outcome

Every check resolves a `verdict` and an `action` from your workflow step configuration. The possible actions are:

- `allow` — no issue, applicant continues
- `flag` — noted on the session for review, applicant continues
- `step-up` — request additional verification (see note below)
- `manual-review` — anti-cheat only; route to a human reviewer
- `block` — stop the flow; **the session is marked failed**

<Info>
  `block` is the only action that fails the session. Every other action is informational or routes the applicant elsewhere in your flow — you decide what happens next.
</Info>

<Note>
  A check only returns `step-up` when its step has an `escalation_type` configured. If a step-up would resolve with no escalation set, the check **downgrades it to `flag`** — you never get a bare `step-up` with no escalation to run. When `step-up` is returned, the response carries an `escalation` object naming the escalation type; you run that step-up yourself (there is no server-side escalation-completion endpoint) and decide how to proceed.
</Note>

## Fail-soft vs. fail-hard

The four analyze checks (injection, VPN, IP jurisdiction, anti-cheat) **fail soft**: when an input is unresolvable (for example, a non-IPv4 address, an unloaded anonymizer feed, or no detectable face), or when the step isn't configured on the workflow (VPN, IP jurisdiction, and anti-cheat only — see above for injection), they return `200` with `UNAVAILABLE`/`allow` rather than blocking spuriously. A request that fails schema validation (a missing required field) returns `400` for injection, VPN detection, and IP jurisdiction — **anti-cheat is the exception**: it fails soft to `200`/`UNAVAILABLE` even on a malformed or missing body. Self-exclusion and purge **management** endpoints **fail hard**: a real error returns `500`, because these calls change registry state and shouldn't fail silently. See [iGaming checks](/igaming/checks) for fail-soft details per check.

## The self-exclusion registry

Each organization maintains its own self-exclusion registry — a list of **identity** entries (a document number) and **face** entries (a session's enrolled face). When a future anti-cheat run scans a document number or matches a face already on the registry, it returns `verdict: SELF_EXCLUSION` and `action: block`. See [Self-exclusion](/igaming/self-exclusion) for how the registry works and how to manage it.
