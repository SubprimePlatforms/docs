> Four common flows, end to end — configure an iGaming workflow, gate onboarding on its checks, exclude an applicant, and purge a face for data deletion.

## Configure an iGaming workflow

Create a workflow with the iGaming steps and the thresholds and actions you want. The workflow's step config is what every check reads for its enforcement — so this is where you customize behavior (which jurisdictions to block, VPN vs Tor handling, dedup sensitivity, self-exclusion). See [Create workflow → Step configuration](/api-reference/workflows/create-workflow#step-configuration) for every field and default.

<Steps>
  <Step title="Create the workflow">
    <CodeGroup>
    ```bash cURL
    curl -X POST https://api.deepidv.com/v1/workflows \
      -H "Content-Type: application/json" \
      -H "x-api-key: YOUR_API_KEY" \
      -d '{
        "name": "iGaming onboarding",
        "steps": [
          { "id": "IP_JURISDICTION", "config": { "blocked_jurisdictions": ["US-WA", "FR"], "out_of_jurisdiction_action": "block", "datacenter_ip_action": "flag" } },
          { "id": "VPN_DETECTION", "config": { "vpn_action": "step-up", "tor_action": "block", "datacenter_action": "block" } },
          { "id": "ANTI_CHEAT", "config": { "action_on_duplicate": "block", "action_on_multi_account": "manual-review", "link_sensitivity": 2, "self_exclusion_enabled": true } }
        ]
      }'
    ```

    ```javascript Node.js
    const response = await fetch("https://api.deepidv.com/v1/workflows", {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "x-api-key": "YOUR_API_KEY",
      },
      body: JSON.stringify({
        name: "iGaming onboarding",
        steps: [
          { id: "IP_JURISDICTION", config: { blocked_jurisdictions: ["US-WA", "FR"], out_of_jurisdiction_action: "block", datacenter_ip_action: "flag" } },
          { id: "VPN_DETECTION", config: { vpn_action: "step-up", tor_action: "block", datacenter_action: "block" } },
          { id: "ANTI_CHEAT", config: { action_on_duplicate: "block", action_on_multi_account: "manual-review", link_sensitivity: 2, self_exclusion_enabled: true } },
        ],
      }),
    });

    const { workflow } = await response.json();
    // reuse workflow.id as workflow_id when you create sessions
    ```
    </CodeGroup>
  </Step>
</Steps>

<Info>
  Omit a step's `config` to accept its defaults, or omit a step entirely to skip that check. Every check reads its thresholds and actions from this step config. VPN detection, IP jurisdiction, and anti-cheat skip evaluation when their step is absent (`UNAVAILABLE`/`allow`). **Injection detection does not skip**: with no `INJECTION_DETECTION` step it still scores whatever signals you send using the defaults (`action_on_detection: block`, `confidence_threshold: 70`), so only call it on sessions whose workflow includes the step. Note the `vpn_action: "step-up"` above only steps up if you also set an `escalation_type` on the step; without one it resolves to `flag`.
</Info>

## Onboarding gate

Create a session **against the workflow above**, run the standalone checks against it one after another, then aggregate the results into a single decision. This is the pattern for an operator-owned sign-up page: your backend holds the API key, your page collects the inputs, and the applicant never leaves your site.

<Steps>
  <Step title="Create a session">
    <CodeGroup>
    ```bash cURL
    curl -X POST https://api.deepidv.com/v1/sessions \
      -H "Content-Type: application/json" \
      -H "x-api-key: YOUR_API_KEY" \
      -d '{
        "first_name": "Jane",
        "last_name": "Smith",
        "email": "jane.smith@example.com",
        "phone": "+15192223333",
        "workflow_id": "wf_igaming_onboarding",
        "send_email_invite": false,
        "send_phone_invite": false
      }'
    ```

    ```javascript Node.js
    const response = await fetch("https://api.deepidv.com/v1/sessions", {
      method: "POST",
      headers: {
        "Content-Type": "application/json",
        "x-api-key": "YOUR_API_KEY",
      },
      body: JSON.stringify({
        first_name: "Jane",
        last_name: "Smith",
        email: "jane.smith@example.com",
        phone: "+15192223333",
        workflow_id: "wf_igaming_onboarding",
        send_email_invite: false,
        send_phone_invite: false,
      }),
    });

    // The session id is returned as `id` (not `session_id`).
    const { id: session_id, session_url } = await response.json();
    ```
    </CodeGroup>

    <Info>
      `send_email_invite` and `send_phone_invite` default to `true`, which emails and texts the applicant a link to deepidv's hosted verification flow. Turn them off when the checks run from your own sign-up page. Keep `session_url` if your workflow also contains hosted steps (for example `ID_VERIFICATION` or `FACE_LIVENESS`) and you want to send the applicant there afterwards. See [Create session](/api-reference/sessions/create-session).
    </Info>
  </Step>

  <Step title="Run VPN detection, IP jurisdiction, and anti-cheat">
    Call each check standalone with the `session_id`, plus the inputs each check requires. `vpn-detection` and `ip-jurisdiction` both require `ip_address`; `anti-cheat` requires `image`.

    <Warning>
      **Run the checks one at a time, not in parallel.** Each check reads the session's analysis data, adds its own result, and writes the whole object back. Concurrent calls race and the last writer wins — the responses are correct, but one check's persisted result is silently dropped from the session.
    </Warning>

    Order matters, too: a check whose action is `block` marks the session **failed**, and anti-cheat returns `UNAVAILABLE` on a failed session. Run the IP checks first and stop early on `block`, or run anti-cheat first if you always want the face enrolled.

    <Note>
      `ip_address` must be the **applicant's** public IPv4 address as your server sees it (the connecting socket address, or the first hop of `X-Forwarded-For` behind a trusted proxy). Do not look the address up from your own server — that returns your server's egress IP and a VPN on the applicant's side is never seen. If you detect the public IP client-side (for example on a localhost build), do it in the applicant's browser so a browser or system VPN exit is what gets checked. Reject private, loopback, and reserved addresses before calling: both IP checks fail **open** on them (`CLEAR` with an `"Unknown"` location, no ASN). The `203.0.113.42` used in these examples is a documentation address and behaves the same way — substitute a real public IP when you try this.
    </Note>

    <CodeGroup>
    ```bash cURL
    curl -X POST https://api.deepidv.com/v1/igaming/vpn-detection \
      -H "Content-Type: application/json" \
      -H "x-api-key: YOUR_API_KEY" \
      -d '{
        "session_id": "b8991ba9-2566-4fe5-b758-66f387c3e28b",
        "ip_address": "203.0.113.42"
      }'

    curl -X POST https://api.deepidv.com/v1/igaming/ip-jurisdiction \
      -H "Content-Type: application/json" \
      -H "x-api-key: YOUR_API_KEY" \
      -d '{
        "session_id": "b8991ba9-2566-4fe5-b758-66f387c3e28b",
        "ip_address": "203.0.113.42"
      }'

    curl -X POST https://api.deepidv.com/v1/igaming/anti-cheat \
      -H "Content-Type: application/json" \
      -H "x-api-key: YOUR_API_KEY" \
      -d '{
        "session_id": "b8991ba9-2566-4fe5-b758-66f387c3e28b",
        "image": "<base64-encoded JPEG>",
        "device_fingerprint": "d3b07384-d9a7-4e1c-9f2a-1c2b3d4e5f60"
      }'
    ```

    ```javascript Node.js
    // The applicant's public IPv4 as seen by your server (e.g. req.ip behind a trusted proxy).
    const ipAddress = "203.0.113.42";

    const calls = [
      {
        path: "ip-jurisdiction",
        body: { session_id, ip_address: ipAddress },
      },
      {
        path: "vpn-detection",
        body: { session_id, ip_address: ipAddress },
      },
      {
        path: "anti-cheat",
        body: {
          session_id,
          image: faceImageBase64, // base64-encoded JPEG, no `data:` prefix
          device_fingerprint: "d3b07384-d9a7-4e1c-9f2a-1c2b3d4e5f60",
        },
      },
    ];

    // Sequential on purpose — see the warning above.
    const results = [];
    for (const { path, body } of calls) {
      const res = await fetch(`https://api.deepidv.com/v1/igaming/${path}`, {
        method: "POST",
        headers: {
          "Content-Type": "application/json",
          "x-api-key": "YOUR_API_KEY",
        },
        body: JSON.stringify(body),
      });
      const result = await res.json();
      results.push(result);
      if (result.action === "block") break; // session is now failed
    }
    ```
    </CodeGroup>

    <Info>
      To add **injection detection**, collect `device_integrity`, `media_source`, and `frame_timing` in the applicant's browser during selfie capture and post them to `POST /v1/igaming/injection` before anti-cheat. The scores are *trust* scores (higher is cleaner). See [Injection detection → Collecting the signals](/api-reference/igaming/injection#collecting-the-signals).
    </Info>
  </Step>

  <Step title="Aggregate the actions">
    Each response includes an `action`. Take the highest-severity action across all results and act on that:

    `block` > `manual-review` / `step-up` > `flag` > `allow`

    ```javascript Node.js
    const severity = { block: 4, "manual-review": 3, "step-up": 3, flag: 2, allow: 1 };

    const worst = results
      .map((r) => r.action)
      .reduce((a, b) => (severity[b] > severity[a] ? b : a), "allow");

    if (worst === "block") {
      // session is already marked failed — deny onboarding
    } else if (worst === "manual-review" || worst === "step-up") {
      // route to a human reviewer or request more verification
    } else if (worst === "flag") {
      // let the applicant through, note the flag for later review
    }
    ```

    <Info>
      If `worst` is `block`, the session is already marked **failed** — you don't need to fail it yourself, just stop onboarding. Treat `UNAVAILABLE` as "no signal", not as a pass.
    </Info>
  </Step>

  <Step title="Read the results later">
    Every check persists its full result on the session. Fetch it with [Retrieve session](/api-reference/sessions/retrieve-session) and read `session_record.analysis_data.ip_jurisdiction_data`, `vpn_detection_data`, `injection_detection_data`, and `anti_cheat_data`. The persisted anti-cheat record is richer than the redacted API response (similarity, matched session, multi-accounting links). A `block` also shows as `"status": "FAILED"`.
  </Step>
</Steps>

## Exclude an applicant

Flag the applicant's face and add their identity to the self-exclusion registry in one call — the preferred way to handle a self-exclusion request. See [Self-exclusion](/igaming/self-exclusion#exclude-an-applicant-preferred-path) for details.

<Steps>
  <Step title="Call the exclude-applicant endpoint">
    <CodeGroup>
    ```bash cURL
    curl -X POST https://api.deepidv.com/v1/igaming/self-exclusion/applicant \
      -H "Content-Type: application/json" \
      -H "x-api-key: YOUR_API_KEY" \
      -d '{ "session_id": "b8991ba9-2566-4fe5-b758-66f387c3e28b" }'
    ```

    ```javascript Node.js
    const response = await fetch(
      "https://api.deepidv.com/v1/igaming/self-exclusion/applicant",
      {
        method: "POST",
        headers: {
          "Content-Type": "application/json",
          "x-api-key": "YOUR_API_KEY",
        },
        body: JSON.stringify({ session_id: "b8991ba9-2566-4fe5-b758-66f387c3e28b" }),
      }
    );

    const result = await response.json();
    ```
    </CodeGroup>
  </Step>

  <Step title="Check for a matched-session fallback">
    If the applicant's session never enrolled its own face — for example, a `DUPLICATE` applicant — the response includes `matched_session_id`, telling you which original enrollment actually got excluded.

    <Info>
      See [Matched-session fallback](/igaming/self-exclusion#matched-session-fallback) for why this happens.
    </Info>
  </Step>
</Steps>

## Purge a face (data deletion)

Remove a session's enrolled face — for a GDPR deletion request or a manual reset.

<Steps>
  <Step title="Call the purge endpoint">
    <CodeGroup>
    ```bash cURL
    curl -X DELETE https://api.deepidv.com/v1/igaming/anti-cheat/b8991ba9-2566-4fe5-b758-66f387c3e28b \
      -H "x-api-key: YOUR_API_KEY"
    ```

    ```javascript Node.js
    const response = await fetch(
      "https://api.deepidv.com/v1/igaming/anti-cheat/b8991ba9-2566-4fe5-b758-66f387c3e28b",
      {
        method: "DELETE",
        headers: { "x-api-key": "YOUR_API_KEY" },
      }
    );
    ```
    </CodeGroup>
  </Step>
</Steps>

<Warning>
  Purge and the other self-exclusion management endpoints fail **hard** — a real error returns `500` instead of falling back to a soft default. Handle errors from these calls explicitly.
</Warning>
