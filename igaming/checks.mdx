> Four checks, one shared model: each reads its workflow step config, resolves a `verdict` and `action`, and persists its result to the session's AnalysisData.

Every check below can run as a [workflow step](/workflows/workflows) or as a [standalone call](/igaming/overview#two-ways-to-run-a-check) against `POST /v1/igaming/{check}` with a `session_id`. Either way, the check's **thresholds and enforcement actions come from its workflow step config** — a standalone request body carries only the check's *inputs* (`ip_address`, `image`, or injection signals), never its config. So configure the step on the session's workflow first (see [Create workflow → Step configuration](/api-reference/workflows/create-workflow#step-configuration)). VPN detection, IP jurisdiction, and anti-cheat skip evaluation when the step is absent (`UNAVAILABLE`/`allow`); injection detection does **not** skip — it scores with the default config (`block` on detection) when its step is missing. Each check writes its result onto the session's AnalysisData, alongside every other check that ran on that session.

<Note>
  All request and response bodies for iGaming endpoints use `snake_case` field names.
</Note>

<Note>
  A check returns the `step-up` action only when its step configures an `escalation_type`. If a step-up would resolve without one, the check **downgrades it to `flag`** — so you never get a bare `step-up` with no escalation to run. (Anti-cheat uses `manual-review` rather than `step-up`.)
</Note>

## Injection detection

Detects virtual cameras, emulators, and injected media during liveness capture — signs the applicant is feeding in fabricated video instead of a live camera feed.

- **Runs as:** workflow step `injection-detection`, or `POST /v1/igaming/injection`
- **Reads:** its workflow step config for thresholds and enforcement — or the **defaults** (`action_on_detection: block`, `automation_handling: block`, `confidence_threshold: 70`) when the workflow has no injection step
- **Inputs:** up to three client-collected signal groups (`device_integrity`, `media_source`, `frame_timing`), each `{ pass, score, signals }` where `score` is a **trust** score, 0–100, higher is cleaner
- **Persists to:** the session's AnalysisData (`injection_detection_data`)
- **Fails soft:** when neither `device_integrity` nor `media_source` is supplied, returns `200` with `UNAVAILABLE` / `allow` rather than blocking the applicant. A request that fails schema validation still returns `400`.

<Warning>
  Unlike the other three checks, injection detection does not skip when its step is absent from the workflow. Only call it on sessions whose workflow includes `INJECTION_DETECTION`, and send `score` as a trust score — a clean capture reported with low scores is treated as a detection.
</Warning>

See the [Injection detection reference](/api-reference/igaming/injection) for the full request and response schema.

## VPN detection

Detects applicants connecting through a VPN, proxy, or other relay that masks their real network location.

- **Runs as:** workflow step `vpn-detection`, or `POST /v1/igaming/vpn-detection`
- **Reads:** its workflow step config for thresholds and enforcement
- **Inputs:** the applicant's public IPv4 address, as seen by your server
- **Persists to:** the session's AnalysisData (`vpn_detection_data`)
- **Fails soft:** when not configured on the workflow, or an input is unresolvable, returns `200` with `UNAVAILABLE` / `allow`. A request that fails schema validation still returns `400`.

<Warning>
  VPN detection is **IPv4-only**. A non-IPv4 address (for example, IPv6) returns `UNAVAILABLE` and fails soft to allow.
</Warning>

See the [VPN detection reference](/api-reference/igaming/vpn-detection) for the full request and response schema.

## IP jurisdiction

Checks whether the applicant's IP address resolves to a jurisdiction you're licensed to serve.

- **Runs as:** workflow step `ip-jurisdiction`, or `POST /v1/igaming/ip-jurisdiction`
- **Reads:** its workflow step config for the allowed/blocked jurisdiction list (country codes like `CA`, or country-subdivision codes like `CA-ON`)
- **Inputs:** the applicant's public IPv4 address, as seen by your server
- **Persists to:** the session's AnalysisData (`ip_jurisdiction_data`)
- **Fails soft:** when not configured on the workflow, or an input is unresolvable, returns `200` with `UNAVAILABLE` / `allow`. A request that fails schema validation still returns `400`.

<Warning>
  IP jurisdiction is **IPv4-only**. A non-IPv4 address (for example, IPv6) returns `UNAVAILABLE` rather than attempting a lookup.
</Warning>

See the [IP jurisdiction reference](/api-reference/igaming/ip-jurisdiction) for the full request and response schema.

## Anti-cheat

Detects duplicate accounts (the same face enrolling under a new identity) and applicants who match an entry on your [self-exclusion registry](/igaming/self-exclusion).

- **Runs as:** workflow step `anti-cheat`, or `POST /v1/igaming/anti-cheat`
- **Reads:** its workflow step config for enforcement, and the session's existing AnalysisData for identity and document signals
- **Inputs:** a base64 JPEG/PNG selfie, plus an optional `device_fingerprint` for multi-accounting linkage
- **Persists to:** the session's AnalysisData (`anti_cheat_data`); on `UNIQUE` it also enrolls the face into your org's dedup collection
- **Fails soft (fully):** unlike the other three checks, anti-cheat *never* returns `400` — a malformed or missing body (bad or absent `image`, missing `session_id`) also returns `200` with `UNAVAILABLE` / `allow`, as does an unconfigured step, an unusable face, or a session that is already in a terminal status (`FAILED`, `REJECTED`, `VOIDED`, `EXPIRED`). It only ever returns `401`/`404` for auth/session errors.

<Info>
  Identity self-exclusion and document/name multi-accounting signals read OCR'd data that's already on the session. Run a document scan step before anti-cheat for full coverage — without it, anti-cheat can still dedup faces, but it can't match on document number or name.
</Info>

See the [Anti-cheat reference](/api-reference/igaming/anti-cheat) for the full request and response schema, and [Self-exclusion](/igaming/self-exclusion) for how enrollment, dedup, and exclusion fit together.

## Verdicts and actions

Each check resolves an `action` from its verdict and your workflow step config. The actions are shared across all four checks:

| Action | Meaning |
| --- | --- |
| `allow` | No issue found; applicant continues |
| `flag` | Noted on the session; applicant continues |
| `step-up` | Additional verification requested |
| `manual-review` | Anti-cheat only; routed to a human reviewer |
| `block` | Flow stops; **the session is marked failed** |

The specific verdict values for each check (for example, anti-cheat's `UNIQUE`, `DUPLICATE`, and `SELF_EXCLUSION`) are documented on each check's reference page, linked above. Every check shares one fail-soft verdict:

| Verdict | When it's returned | Resulting action |
| --- | --- | --- |
| `UNAVAILABLE` | Not configured on the workflow (VPN, IP jurisdiction, anti-cheat), an unresolvable input, a terminal session (anti-cheat), or an internal error while running the check | `allow` |
